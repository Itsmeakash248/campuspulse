CampusPulse SSWD Project Report Section 1: Executive Abstract & Introduction

Executive abstract

In contemporary university computer science education, laboratory environments serve as the crucible where theoretical constructs materialize into operational software systems. However, managing physical computing infrastructure, tracking concurrent workstation utilization, resolving rapid hardware/software incidents, and evaluating hundreds of student laboratory programs remain overwhelmingly bottlenecked by fragmented manual paper registers. CampusPulse is a comprehensive, production-grade web platform engineered specifically for the Server Side Web Development (SSWD) curriculum at KLE Technological University, Hubballi.

Engineered with a modular Node.js runtime, an Express.js RESTful routing architecture, and a schema-validated Supabase Postgres store, CampusPulse establishes end-to-end telemetry across all 40 physical workstations in BCA Lab 302. The platform introduces: (1) a real-time terminal map showing hardware specifications and student occupancy, (2) an SLA-driven grievance escalation engine with priority ticketing, and (3) a digital laboratory journal verification desk supporting all 39 course laboratory programs with automated syntax linting, plagiarism similarity indexing, and faculty viva grading.

1. Introduction to the project

1.1 Background & Context

The Department of Bachelor of Computer Applications (BCA) at KLE Technological University conducts intensive practical sessions in Server Side Web Development (SSWD - Course Code 24BCA304). The syllabus encompasses modern ECMAScript standards, asynchronous EventLoop processing, file stream manipulation, custom HTTP server orchestration, Express middleware design, and both MongoDB and relational (Postgres) CRUD operations. A dedicated batch of 60 students utilizes BCA Lab 302 across 40 networked workstation terminals.

1.2 Architectural Motivation

Prior to CampusPulse, lab attendance, terminal assignment, and incident reporting were tracked in physical paper logbooks. When a student encountered a peripheral failure (e.g., keyboard key defect, network disconnection during npm install, or database service daemon permission locks), reporting the incident required manual physical intervention. Furthermore, evaluating the 39 required SSWD laboratory programs consumed hours of laboratory time due to manual code review and viva verification. CampusPulse transitions these workflows into an instantaneous, asynchronous server-side web platform.

CampusPulse SSWD Project Report Section 2 & 3: Problem Statement & Objectives

2. Problem statement

Laboratory administration in academic institutions faces persistent friction due to the lack of interconnected server-side systems. Specifically, the operation of BCA Lab 302 under the SSWD curriculum exhibited the following critical problems:

  1. Uncontrolled Workstation Concurrency & Resource Contention: With 60 students enrolled and 40 physical workstations, simultaneous check-ins led to seat disputes, unverified system occupancy, and untracked terminal swapping during active coding evaluations.
  2. Latent Hardware & Software Incident Resolution: High-demand programming tasks (such as running multi-threaded Node.js scripts, compiling native C++ bindings, or running local database daemons) frequently encounter hardware peripheral faults or network socket drops. In the absence of a computerized triage system, workstations remained in unmonitored downtime for days.
  3. Evaluation Bottlenecks Across 39 Prescribed Lab Programs: The SSWD curriculum mandates rigorous completion of 39 foundational laboratory programs. Manually grading code structure, checking plagiarism, and recording viva marks across 60 students represents 2,340 individual evaluation transactions per semester, causing substantial grading latency.
  4. Absence of Verifiable Audit Logs & Academic Accountability: Physical logs cannot prevent unauthorized retro-active timestamping or maintain tamper-evident historical operational records required for university academic quality audits (NBA / NAAC compliance).

3. Objectives of the project

The primary aim of CampusPulse is to engineer a resilient, highly available server-side platform resolving the aforementioned institutional challenges. The core objectives are systematically defined as follows:

  • Real-Time 40-Terminal Telemetry Engine: Develop a dynamic server-side resource registry mapping the operational state (Available, Occupied, Maintenance, Offline), hardware specifications, IP allocations, and active student USNs for all 40 workstations in BCA Lab 302.
  • SLA-Driven Grievance Escalation & Incident Management: Implement a schema-checked RESTful ticketing pipeline that categorizes incidents into Hardware, Software, Network, Peripheral, and Power, automatically enforcing Service Level Agreement (SLA) timers of 60, 120, and 240 minutes.
  • Digital Laboratory Journal Verification Desk: Provide an integrated evaluation portal tracking student progress across all 39 SSWD syllabus programs, providing automated syntax validation, plagiarism score calculations, and faculty viva grading with instant 10-mark scoring.
  • Strict Academic Report & Journal Integration: Design an A4 print engine with precise page boundaries, allowing students to generate an official 10-page project report complete with faculty sign-off and university credentials for attachment to their physical journal.
  • RESTful API Architecture & Concurrency Control: Adhere to modern Server Side Web Development conventions by implementing decoupled Express route handlers, CORS-compliant gateways, centralized error-handling middleware, and Postgres constraints enforced through Supabase.

4. Scope of the project

4.1 Functional Scope

CampusPulse encompasses role-based workflows for students, faculty guides (Prof. Aruna Mam), and laboratory systems administrators. Its functional boundaries include:

  • Workstation Asset Management: 40 workstation nodes with seat booking, status updates, specs inspection, and release operations.
  • Incident Lifecycle Management: Ticket generation, priority assignment (Low, Medium, High, Critical), status transitions (PENDING → IN_REVIEW → RESOLVED → CLOSED), and resolution note logging.
  • Laboratory Journal Workflow: Program submissions (Programs 1-39), automated syntax parsing, plagiarism score computation, and viva marks recording.
  • Operational Analytics: Live metric computation for lab utilization rate, incident category frequencies, and submission velocities.

4.2 Non-Functional Scope & Scalability

The system is designed with sub-50ms API response latency, asynchronous non-blocking event loop execution, responsive mobile/desktop interfaces, and strict A4 printable styling conforming to ISO 216 dimensions (210mm x 297mm).

6. Database design / tables (part 1)

6.1 Database Architectural Overview

CampusPulse persists its operational data in a Supabase-hosted Postgres database. Six relational tables hold workstations, allocation sessions, grievance tickets, journal submissions, users, and audit events, while a JSONB column carries variable hardware specifications. Postgres CHECK constraints enforce status and priority domains, indexes support the live dashboard queries, and Row Level Security blocks direct client access. Only the Express server writes to the database through the service-role key, which never leaves the server. A mapper layer translates snake_case rows into the camelCase JSON contract consumed by the browser.

7.1 Express Application Bootstrap & Middleware Pipeline (server.js)

Demonstrates the server instantiation, CORS configuration, JSON body parsing, custom HTTP request latency logging middleware, static asset routing, and centralized error handling middleware.

// server.js: Express Server Runtime & Pipeline const env = require('./config/env'); const express = require('express'); const cors = require('cors'); const path = require('path'); const apiRouter = require('./routes/api'); const store = require('./models/store'); const app = express(); const PORT = env.PORT || 3000; // Security & Parsing Middleware app.use(cors()); app.use(express.json()); app.use(express.urlencoded({ extended: true })); // Custom Request Logger Middleware with High-Resolution Latency app.use((req, res, next) => { const start = Date.now(); res.on('finish', () => { const elapsed = Date.now() - start; console.log(`[${new Date().toISOString()}] ${req.method} ${req.url} ${res.statusCode} (${elapsed}ms)`); }); next(); }); // Mount Static Application and REST API Gateway app.use(express.static(path.join(__dirname, 'public'))); app.use('/api', apiRouter); // Centralized Asynchronous Error Handler Middleware app.use((err, req, res, next) => { console.error('[UNCAUGHT EXCEPTION]', err.stack); res.status(500).json({ success: false, error: 'Internal Server Error', message: err.message }); }); app.listen(PORT, () => { console.log(`CampusPulse Server active on port ${PORT} | Data store: ${store.mode}`); });

7.2 RESTful Workstation Allocation Controller (routes/api.js)

Validates student seat allocation requests, checks workstation concurrency status, calls the Supabase-backed store adapter, and records audit telemetry.

// routes/api.js: Workstation Allocation Controller router.post('/lab-assets/:tag/allocate', asyncHandler(async (req, res) => { const tag = req.params.tag.toUpperCase(); const { usn, studentName, purpose } = req.body; if (!usn || !studentName) { return res.status(400).json({ success: false, error: 'USN and name required.' }); } const asset = await store.labAssets.findById(tag); if (!asset) return res.status(404).json({ success: false, error: 'Workstation not found.' }); if (asset.status === 'occupied') { return res.status(409).json({ success: false, error: `Occupied by ${asset.studentName}` }); } const updatedAsset = await store.labAssets.updateStatus(tag, 'occupied', { usn, studentName, currentProgram: purpose || 'Active SSWD Lab Session' }); await store.allocations.create({ workstationTag: tag, seatNo: updatedAsset.seatNo, usn, studentName, sessionPurpose: purpose || 'General SSWD Laboratory Practice' }); await store.auditLogs.create({ action: 'WORKSTATION_ALLOCATED', actor: usn, details: `Seat ${tag} assigned to ${studentName}`, ip: req.ip || '127.0.0.1' }); res.status(200).json({ success: true, message: `Allocated ${tag}`, asset: updatedAsset }); }));
